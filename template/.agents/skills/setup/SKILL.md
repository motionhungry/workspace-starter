---
name: setup
description: Set up an Obsidian vault, resume incomplete setup, or open an existing vault on a new computer.
---

Work from the vault root. Reuse existing choices and ask only about unresolved ones.

Guide the operator through one choice at a time. Start with one sentence about what is ready, then ask one plain-language question. Give click-by-click instructions when the operator chooses an option that needs action. Keep commit IDs, remote names, branch names, and discovery details for troubleshooting or when the choice depends on them.

For a decision with two or three clear options, use the session’s built-in choice picker when available. Otherwise, present a short numbered list in chat. Put the recommendation first and include **Decide later** when deferral is supported. Wait for the operator’s answer before acting on that choice. Confirm the actual backup destination and policy separately before the first backup.

For vault backup, explain that a private Git repository holds the vault’s change history and lets the operator restore it on another computer. Recommend Google Shared Drive separately for media stored outside the vault. Offer to use an existing private repository, walk them through creating one, or continue with local work and set up backup later. For GitHub, after they choose to create one, guide them to **New repository**, choose **Private**, leave the initialization options unchecked, and ask them to share the repository link. Use the [backup instructions](references/settings-and-backup.md) to confirm the destination and settings. Present any technical settings that need approval as one recommended bundle and explain what it does.

1. **Inspect the vault.** Verify local file and command access, Git 2.28+, and Python 3.9+. Inspect `90 System Development/workflow-settings.json`, ignored `.agents/local.json` if present, and Git state if initialized. Investigate missing provenance before editing and preserve existing work. Use the [first-proposal procedure](references/first-proposal.md) to find any existing proposal.
2. **Verify Obsidian and backup.** If Obsidian access is unverified, tell the operator how to use **Open folder as vault** and what to look for. Use desktop controls only if the operator asks. When the vault is already open and the Obsidian CLI is enabled, a read-only check can confirm the vault and expected folders. Record an unconfirmed check as pending and continue. Follow [settings and Git backup](references/settings-and-backup.md) to verify local Git history and identity, including when resuming older setups. Offer remote backup as an optional step. If backup is pending, preserve local work and continue once the vault is locally usable.
3. **Configure media, updates, and skill discovery.** Follow [media setup](references/media.md) when the destination is undecided or access needs checking. If the operator has yet to choose, offer to install a skill for checking starter updates on request. Record `starter.update_review` as `enabled` or `declined`. If enabled, use `python3 .agents/skills/setup/scripts/workspace.py enable-updates` to install it. Preserve its edits and review history. Follow [skill discovery](references/discovery.md) when configuring a new copy or checking discovery in a fresh session.
4. **Checkpoint and continue.** Commit reviewed setup files locally. Push if backup is approved and report any pending backup. Once the local vault is usable, follow the [first-proposal procedure](references/first-proposal.md) to learn the workspace purpose, use the [folder order](../../../README.md#folder-order) for any folders proposed for that purpose, and hand off to [System Development](../system-development/SKILL.md) if the first proposal is absent. On resumption, report the existing proposal and handle pending checks. If an existing proposal is uncommitted, validate and checkpoint it. When backup is enabled later, commit the reviewed backup settings and push the existing history. Retry an unpushed commit without restaging it.
